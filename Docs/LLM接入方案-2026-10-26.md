# 有径 · LLM 生成通道现状与接入方案

> 2026-10-26。**本文档只盘点与提案，未改动任何代码**；所有落点都等用户拍板后排期（工程纪律「决策不抢跑」）。
> 背景条款：`Docs/有径·App开发文档.md` §2.4（AI 能力方案）、§3.3（三层数据分层）、§4.3（Schema 三层防线）。
> 代码事实以 `entry/src/main/ets/ai/LlmClient.ets` 当前版本为准。

## 一、现状：生成管线已全通，唯一缺口是「真模型」

主链形态（真机已完整跑通，当前走 mock 传输）：

```
PromptBuilder.buildRequest（系统提示内嵌完整 JSON Schema，第一层防线）
  → LlmTransport.complete()
  → TripParser.parseTrip() 逐字段类型守卫（第三层防线）
  → Trip → TripDao.saveTrip 落库 → 屏8 渲染
  失败重试 1 次 → 仍失败抛 TRIP_GENERATE_RETRY_EXHAUSTED → 屏7 降级
```

传输层有两个实现（`ai/LlmClient.ets`），由 `MockConfig.USE_MOCK_DATA` 在
`LlmClient.generateTrip` 里二选一：

| 实现 | 状态 | 说明 |
|---|---|---|
| `MockLlmTransport` | **当前默认**（`USE_MOCK_DATA=true`） | 按请求参数确定性合成合法 Trip JSON，走完整「响应→守卫→Trip」链路，管线等价性已验证；但内容是合成的，`overview.summary` 带「离线合成」字样 |
| `HttpLlmTransport` | 骨架就绪、未接通 | OpenAI 兼容 chat/completions 形态；已实现 `response_format: json_schema {strict:true}`（§4.3 第二层防线，schema 与另两层同源 `TripSchema.TRIP_JSON_SCHEMA`）；端点取 `ApiConfig` 单点，两值为空即抛 `LLM_UNAVAILABLE`——失败路径真机实测过（§4c：屏7 显示「LLM 端点未配置」+ 两条修法可跳转） |

### HttpLlmTransport 接通前必须补的三件事

1. **鉴权头**：现请求头只有 `Content-Type`，没有 `Authorization` / API-Key 的注入点。
2. **Key 管理**：文件头注释承诺「Key 走 HUKS」，但 HUKS 代码尚不存在。需要：Key 的写入入口（开发期可先走本地不入库的配置，上架前必须收进 HUKS）、读取、禁止明文落盘。
3. **超时参数**：`http.createHttp().request()` 未设 `connectTimeout` / `readTimeout`。屏6 已有 `cancelled` 短路（用户取消后不再进屏8），但传输层自身无超时兜底，慢端点会把生成页吊住。

### 相关现状的两点更正 / 说明

- **小艺 Skill 平台侧已不是缺口**：2026-10-23 已按「仅自己使用」上架 `1.0.0`（`Docs/小艺Skill接入清单.md` §F 全部打勾，控制台状态「已上架」）。早前文档里「平台侧待用户操作」的表述以该清单为准。
- **应用内 Skill 只是入口，不是生成通道**：`youjing-plan-trip` 做的是「记下目的地/日期/天数/人数 → 预填屏2」，生成仍完全走 `LlmClient`。开发文档 §2.4 说的「小艺开放平台 LLM 模式 Agent」是另一件事（平台侧的生成大脑），目前未创建。

### 第二层「AI 精选」仍是确定性替身

§3.3 的三层分层中，第二层（AI 帮用户勾选/排序）当前由 App 端规则承担：景点每组取热度 top-N（`SpotPickPage`），住宿区域按与所选景点的平均直线距离排序取前 3（`StayPickPage.rankByDistance`）。链路形态与文档一致，接真 LLM 后按文档把这一步换成独立精选调用即可。

## 二、两条路线对比（等用户拍板）

| 维度 | 路线 A：小艺开放平台「LLM 模式」Agent | 路线 B：直连 LLM HTTP API |
|---|---|---|
| 成本 | 平台承担算力（开发文档 §2.4 推荐理由） | 自担，按 token 计费；Prompt 内嵌完整 Schema + 精简景点列表，单次请求量可观（`MockTransport` 日志已打 system/user 字节数，可先估算） |
| 前置 | 平台控制台创建 LLM 模式 Agent + 工作流编排；**接入协议需先调研**（`ApiConfig` 注释「待调研」即指此事），公开资料有限 | 用户定三件事：服务选型、端点 URL、API Key 来源与预算 |
| 工作量 | 不可控（依赖平台调研 + 审核 1–3 个工作日 + 协议适配） | 一天级：补 §一 的三件事 + 翻开关 |
| 风险 | 平台协议/配额不受控；审核延迟（§8 已列风险） | Key 的端侧管理责任（HUKS 防落盘明文，防不了已 root 环境）；国内网络与合规选型 |
| 与现有代码的关系 | 新增第三个 `LlmTransport` 实现，传输抽象已就位 | 用现成的 `HttpLlmTransport` |

**不互斥**：传输层是接口化的，A、B 可以并存（B 先行验证规划质量，A 接入后按账号/网络环境选择）。若目标是尽快让真实模型进主链验证，建议先 B；A 作为降本路线并行调研。
