### 为什么 Skill 脚本能离线跑

`PlanTripSkill.ets` 依赖四个 kit：`@kit.AbilityKit`（scriptManager 回调）、`@kit.BasicServicesKit`（BusinessError）、`@kit.ArkData`（preferences）、`@kit.PerformanceAnalysisKit`（hilog）。替身只补这几个符号：

- **`scriptManager.completeArkTSScriptInApp`** 把回包存进全局数组让断言取用；
- **`preferences` 替身按 name 分桶、跨调用保持同一桶**——这点是必须的：`SkillPrefill.save` 与 `take` 是两次 `getPreferencesSync`，每次返回新桶的话「取后即删」会成假绿；
- **`startAbility` 替身按手机语义抛 201**（真机后台拉起就是这个错），脚本必须自己吞掉并仍回 success。

### 断言覆盖（13 组 / 120 条）

1. 四城白名单 + 四参映射（destination / startDate / days / people / route）
2. 非四城 → `ERR_INVALID_PARAMS` + suggestion 列出全部四个支持城市
3. 非法日期（`2026-02-30` / `13月` / `32日` / 空 / 非 ISO / `2026-1-1`）→ 拒绝
4. 天数与人数越界（`0` / `31` / `100` / 负数 / 小数 / 非数字）→ 拒绝
5. 省略天数人数 → 默认 3 天 2 人
6. **过去日期 → 拒绝**（修缺陷 A 后由「接受」改为「拒绝」，附 suggestion 文案断言）
6b. **当天与将来的日期 → 照常接受**
6c. **`days=1` → days 就是 1**（修缺陷 B 的 Skill 侧）
7. message 文案含目的地/日期/天数/人数四要素 + 手机上 `launched=false`
8. `SkillPrefill` **取后即删**
9. 超过 2 小时的预填被拒
10. 非法字段预填被拒（空城市 / 假日期 / days 与 people 越界）
11. `clear` 后为空

> **日期用例相对「今天」生成**：写死 `2026-12-01` 的话，过了那天它就集体变成过去日期，
> 用例会从「应成功」变成「应失败」而集体误报——那正是缺陷 A 的判据本身。
> 真机探针同理，日期全部按**设备当天**推算。

## 四、发现的 2 条缺陷 → 修复

两条都在**预填消费侧**，不在 Skill 脚本里。

### 缺陷 A · 过去日期被静默改写（Skill 与 Want 两条路径都中）→ 已修

**修前现象：** 下发过去日期，入口日志说预填成功，屏2 却显示今天起算。

```
入口日志：外部预填 route=TripInput 广州 2026-08-01→2026-08-04 3人
屏2 实测：11月13日 – 11月15日 / 3天2晚          ← 与日志对不上
```

**根因：** `entry/src/main/ets/pages/TripInputPage.ets:104`（修前）

```ts
if (DateUtils.isValidIsoDate(b.startDate) && b.startDate >= today) {
  this.startDate = b.startDate;
}
```

草稿里的出发日早于今天就被丢弃，屏2 回落到「今天起算 3 天」。它**不区分草稿来源**——小艺明确传来的用户意图也被一起丢掉了，且**没有任何提示**。这与同文件「不静默改成北京——那会让『小艺说已记下杭州、界面显示北京』对不上」的原则正好相反。

**修法（三层，各司其职）：**

1. **Skill 脚本入口直接拒**（`entry/skills/youjing-plan-trip/scripts/PlanTripSkill.ets:75`）

   ```ts
   if (!DateUtils.isUpcoming(start, DateUtils.todayIso())) {
     return invalid('start ... is in the past',
       '出发日期 ... 已经过去了，请给一个今天或将来的日期。');
   }
   ```

   小艺拿到的不是「成功记下了 8 月 1 日」，而是一条可执行 suggestion——它会如实追问将来的日期，
   **不产生无法兑现的口头承诺**。
2. **深链 Want 侧照写草稿**（`EntryAbility.ets:633`）：过期只记一条 warn，不静默丢弃。
   承诺方不同、处理就不同：Want 没有人格化回复，明示即可。
3. **屏2 统一改写并明示**（`TripInputPage.ets:113-163`）：过期日期改写为今天起算，
   **长度保住**（请求 4 天就还是 4 天，不回落成默认 3 天），并弹 toast + 写日志。

新增 `DateUtils.isUpcoming`（`utils/DateUtils.ets:38`）作为唯一判据；ISO 定长零填充，字典序即时间序。

**修后实测：** 见 §三 [2] 最后一条与 §三 [3] 截图。

### 缺陷 B · Want 路径 days=1 被当成 3 天（Skill 路径无此问题）→ 已修

**修前现象：** `days=1` 下发过去，屏2 显示 3 天 2 晚。

**根因：** `entry/src/main/ets/entryability/EntryAbility.ets:625`（修前）

```ts
if (days > 1 && DateUtils.isValidIsoDate(basic.startDate)) {   // ← days=1 被这个门槛挡掉
```

`days=1` 不满足 `days > 1`，`endDate` 不被写，屏2 于是回落到默认 3 天。而 Skill 路径
（`applySkillPrefill`）无条件算 `endDate = addDays(start, days - 1)`，`days=1` 得到
`endDate == start`，屏2 的 `spanDays >= 1` 门槛放行 → 显示 1 天。**同一句话，两个入口两种天数。**

**修法：**

- `applyWant` 改成 `days >= 1` 口径，且区间收敛到共享常量（`EntryAbility.ets:647`）：

  ```ts
  if (!TripLimits.isDaysValid(days)) { /* 忽略并记日志 */ }
  else if (endValid) { /* 显式 end 优先 */ }
  else if (DateUtils.isValidIsoDate(basic.startDate)) {
    basic.endDate = DateUtils.addDays(basic.startDate, days - 1);
  }
  ```

- 新增 `entry/src/main/ets/utils/TripLimits.ets`：**全工程唯一的区间口径**
  （天数 1–30、人数 1–30），Skill 脚本、深链 Want、草稿预填校验共用——改边界只改一处。
- 人数同样收敛到 `TripLimits.isPeopleValid`（`EntryAbility.ets:658`），越界记日志忽略。

**修后实测：** `days=1 → 屏2 显示 1月12日 – 1月12日 / 1天`（§三 [2]）。
