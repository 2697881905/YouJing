## 二、发现（按严重度）

### F1 · [P1] 地图 tab 根页永远空态，即使行程存在（回归）

证据链（全部可静态断言）：

1. `pages/Index.ets:101`：`TabContent() { MapPage({ rootMode: true }) }` —— **不传 `tripId`**；
2. `pages/MapPage.ets:39`：`@Prop tripId: string = ''`，且 MapPage **不 import / 不读
   `ACTIVE_TRIP_KEY`**（全文件无 AppStorage 消费）；
3. `pages/MapPage.ets:62-65`：`reload()` 在 `tripId` 为空串时直接 `loaded = true; return`；
4. `pages/MapPage.ets:227`：空态文案「先从『我的行程』选一条行程」——而「我的行程」里的
   行程并不会被地图 tab 用上，这句引导在行程存在时是误导；
5. `pages/MapPage.ets:266-268`：`.onShown(reload)` **只挂在 `HdsNavDestination` 分支**，
   `rootMode` 分支没有任何生命周期钩子——即使补传 tripId，切 tab 回来也不会重载。

旁证：`45923da` 提交信息的 run4 验收清单写的是「费用/**我的**根页正文照旧真数据」，
地图 tab 正文不在其中。

**根因**：`ACTIVE_TRIP_KEY` 全库变成只写不读（写方：Index 种子 `Index.ets:57-63`、
`EntryAbility.ets:211`、`ExpensePage.ets:152`、`ItineraryPage.ets:69`、`OnTripPage.ets:120`；
读方：**零**）。§4j-3 那条「种子先等 `AccountStore.init` 再写」的分区修复，服务的正是这个键
——现在键没人消费，种子成了精心排序的死代码，地图 tab 则在重构中丢了唯一的数据入口。

**修法方向**（供定夺，未动代码）：恢复消费方——Index 把
`@StorageLink(ACTIVE_TRIP_KEY)` 传给 `MapPage({ tripId })`（@Prop 随父值异步落定而更新），
MapPage 加 `@Watch('tripId') → reload()`，并在 rootMode 分支补可见性重载钩子；
或 MapPage 根模式自读 `ACTIVE_TRIP_KEY`。无论哪条，F2/F3 同根，宜一并设计。

### F2 · [P2] 深链 `route=Expense` 等非行程 tab 的参数被静默丢弃

`EntryAbility.ets:207-220` `routeTo`：非行程 tab 现在只写 `TAB_INDEX_KEY`（+ param 写入
`ACTIVE_TRIP_KEY`），**不再 push**——这是 ④ 的修法，本身成立。但代价是：

- `ExpensePage` 根模式 `reload()`（`ExpensePage.ets:130-145`）在 `tripId` 为空时走
  `listSummaries` 取 `rows[0]`，**不读 `ACTIVE_TRIP_KEY`**；
- 于是深链指定的 tripId 无效，费用 tab 永远展示「最近一条行程」；
- 旧行为（TabRootHost push 带参）是带 `tripId` 精确打开的。

影响面：当前带 `route=Expense` 参数的深链只有验收脚本与外部测试在用，用户可见面小；
但「带参深链」是文档承诺的通道（§6 阶段 9），值得收口。与 F1 同根同修。

### F3 · [P2，待真机判] 冷启直落费用 tab 的账号分区竞态

时序推演：冷启 `--ps route Expense` 时 `ExpensePage.aboutToAppear`（→ `reload()` →
`listSummaries`）跑在 `EntryAbility.bootstrap` 的 `await AccountStore.init` 完成之前
——§4j-3 记录的正是这个时序。此时 `AccountStore.uid()` 还是游客键：

- 游客分区通常为空（首次登录已 `adoptGuestData` 归户）→ `listSummaries` 返回空 →
  费用页空态，且 Index 种子完成后**没有任何机制通知 ExpensePage 重查**（无 `@Watch`）；
- §4j-3 的修复只覆盖了 Index 自己那条种子路径，页面自查这条新路径没接等待。

复现建议：杀进程 → `aa start --ps route Expense`（真账号名下有行程）→ 预计空态。
run4 的「费用根页真数据」大概率跑在 warm 进程或游客分区尚有数据的状态，未覆盖此窗口。
**标注：本条是时序推演，非实测**——需要一次真机复现定性。

### F4 · [P3] `AppNav` 死常量

`common/constants/AppNav.ets:28-29` 的 `PENDING_ROUTE_KEY` / `PENDING_PARAM_KEY`
全库零引用（TabRootHost 与 EntryAbility 的消费方都删了）。按工程死代码清理惯例应删；
若 F1/F2 的修复决定恢复「待路由」机制则例外。

## 三、确认成立的部分（正面清单）

  push」与我上一轮静态审查的推断一致；删掉 pending-push 整条路是正解，不是掩盖。

  `AppRouter ↔ 页面` 循环 import 实测可编（routerMap 是提升的函数声明）。
